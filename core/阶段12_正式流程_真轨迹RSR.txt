一、本期一句话目标
--------------------------------
把 RSR 从「能演示校准流程（常靠伪对照）」升级为：
**有真机轨迹就必须优先用真轨迹；没有真机轨迹时仍可正常伪对照，且页面/实验记录写清楚。**

「硬门槛」在这里的含义（务必对齐）：
- ✅ 硬的是规则：一旦收到合格真轨迹 → 禁止静默改用伪对照冒充
- ❌ 不是：没接真机就做不了第12期 / 产品不能演示


二、你的产品能获得什么（相对前面）
--------------------------------
| 维度 | 第7期管道 + 第11期联调 + 能力可见 | 第12期之后 |
|---|---|---|
| 对照数据 | 多数伪对照；真轨迹字段已预留 | 真轨迹优先成为可验收规则 |
| 无真机 | 伪对照可演示 | **同样可正常伪对照**（保底不变） |
| 有真机回传 | 契约可选 trajectory，未当硬规则验 | 假接收端/烟雾可造真轨迹；规则 + 验收锁死 |
| 对外故事 | 「能联真机 + 能演校准」 | 「校准在吃真机数据（有则必用）」 |
| 现实用处 | 软件链路通 | 试机参数更可能贴近真臂偏差（仍非产线抓取） |

四、现状盘点（推导依据 · 代码已有）
--------------------------------
已有（因此第12期是「收口规则 + 补洞」，不是从零造 RSR）：
1. `run_rsr_iteration`：已先 `extract_real_trajectory`，没有才伪对照
2. 契约：`normalize_execute_ack` 可保留 `trajectory`；校验「若有则须为 list」
3. `HttpRobot`：原始响应在 `data.response`；提取函数已能读 `data.response.trajectory`
4. 网站：RSR 状态条已能显示「伪对照 / 真轨迹 / 不会做校准」
5. 假接收端：第11期默认只回 ok/message，**尚未稳定回传演示用真轨迹**

缺口（第12期要补）：
A. 提取路径不够齐：`data.ack.trajectory` 等旁路可能漏读（有轨迹却误判伪对照 → 硬规则失效）
B. 假接收端缺少「可选回传轨迹」模式 → 无实验室时无法端到端验「真轨迹优先」
C. 轨迹最小形状未写成可测约定（帧字段、空列表、维数不对时怎么办）
D. Pipeline 里 `allow_pseudo_real=True` 写死；缺少「策略可见」与实验旁路字段（如 `rsr_policy`）
E. 总验收口令尚未把「有轨迹→必须 robot；无轨迹→pseudo」锁成烟雾


五、自行推导可行性
--------------------------------
| 项 | 评级 | 理由 |
|---|---|---|
| 规则：有真轨迹禁止静默伪对照 | **高** | 逻辑已在 rsr_loop；补提取路径 + 断言即可 |
| 无真机时伪对照保底 | **高** | 现网已通；本期明确「不删保底」即可 |
| 假接收端可选回传轨迹 | **高** | 本地脚本可控；不依赖实验室排期 |
| 轨迹最小形状约定 | **高** | 沿用现有 `{t, joint_positions}`；只增校验不改主契约 |
| 网站文案/诊断加固 | **高** | 能力可见步骤4已铺好，本期少量对齐 |
| 实验记录可区分对照来源 | **高** | 已有 `rsr_reference_source`；可补 policy/帧数摘要 |
| 真实实验室臂回传质量 | **中** | 格式/频率/坐标系靠对方；软件侧只定契约+友好失败 |
| 用真轨迹校准后仿真「明显更像真臂」 | **中** | 参数校准是有界微调，不是魔法；答辩应说「对齐试机」非「已等同真机」 |
| 无真机却把第12期当「必须上真臂」 | **低（不推荐）** | 会拖垮节奏；与你们「伪对照可演示」约定冲突 |

总体结论（自主定案）：
- **第12期在未接真机时完全可做、可验收**——用假接收端「带 trajectory 模式」代替实验室。
- **接上真机后**只需对方按同一 JSON 回轨迹，规则自动吃真货。
- 风险主要在「漏提取导致有轨迹仍走伪对照」与「空/坏轨迹处理不清」——用步骤1–2专门堵住。


六、不超过 5 个小步骤
--------------------------------
步骤1：真轨迹契约与提取加固
  - 约定最小帧：`[{ "t": number, "joint_positions": [number, ...] }, ...]`
  - `extract_real_trajectory` 覆盖：data / data.response / data.ack（及已有别名键）
  - 空列表、非 list、关节维数明显异常 → 视为「无合格真轨迹」，走伪对照或 skip（策略在步骤3）
  - 验证：单元烟雾：有 ack.trajectory 也能提成 robot；坏数据不崩

步骤2：假接收端「可选回传轨迹」
  - 默认行为保持第11期（可只回 ok/message）→ 无轨迹时伪对照仍通
  - 增加开关/参数（如 `--with-trajectory`）：用请求里仿真无关的可重复假关节序列，或固定短轨迹，**形状合格且 reference 能被识别为真轨迹来源**
  - 验证：本机 HTTP 真发 + 该模式 → RSR 的 `reference_source=robot`

步骤3：RSR 策略显式化（硬门槛落点）
  - 默认策略：`prefer_real` = 有合格真轨迹用真；否则允许伪对照（未接真机正常演示）
  - 可选收紧（默认关）：`RSR_REQUIRE_REAL_TRAJECTORY=true` 时无真轨迹则 skip（给实验室严模式，不作为演示默认）
  - 返回/实验旁路增加只读字段：如 `reference_source`、`reference_frame_count`、`policy`（只增不改主契约）
  - 验证：同一次勾选 RSR：无轨迹→pseudo；有轨迹→robot；严模式无轨迹→skipped

步骤4：网站与清单对齐（提示不膨胀功能）
  - 诊断/摘要已有「伪对照/真轨迹」：对齐新字段；坏轨迹友好一句
  - 更新 `真机联调检查清单`：第12期勾选项（对方如何回 trajectory）
  - 验证：关真发仍可伪对照；开假接收端带轨迹能看出「真轨迹」

步骤5：总验 + 回归 + 勘误
  - 烟雾：无轨迹伪对照；有轨迹真优先；严模式 skip；复跑 phase11 / feature_visible 相关
  - 书面确认：未接真机可演示；未默认开真发；未堵死第13期接触抓取
  - 勘误入库；总规划第12期勾完成态
